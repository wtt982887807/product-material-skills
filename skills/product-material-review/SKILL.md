# 按合同制作与审阅产品物料

**合同提供目标产品及内容，其他上传文件默认提供格式模板。** 模板可以属于不同产品，不以模板与合同不同名阻塞制作。核对时让模板反向提出需求，再回查合同补提；字段字典帮助复用已有口径，不是允许提取的白名单。AI 负责语义发现、适用性判断和审阅，CLI 校验来源、位置、关联、状态及实际输出；用户无需编写 JSON。

## 开始前

需要一份主合同和至少一份 PPT、一页通或海报模板。合同支持 DOCX、可提取文字的 PDF；旧 DOC 需要先取得转换版并用 `register-conversion` 登记匹配来源哈希的缓存。回写支持 DOCX 和 PPTX，图片海报或 PDF 一页通不属于自动回写格式。合同自身的身份或版本冲突仍需核对；不以模板、文件名或 `--product` 覆盖合同身份。

**Word 物料先接受旧修订，再生成本次修订。** `analyze` 默认在工作副本中接受原有全部修订，以清洁基线分析和回写；上传原件保留，原批注保留并可追加。存在历史修订时须使用 Windows Microsoft Word 原生 `AcceptAllRevisions`；无历史修订不需要 Office 完成准备。无法原生接受时明确受阻，不能保留旧历史直接交付或声称已接受。此准备仅针对物料，不处理合同的修订。具体路径和来源绑定见 [CLI](references/cli.md#word-物料准备)。

`analyze` 默认 `--material-mode template`。仅当用户要核对已有同产品物料时使用 `--material-mode review`。两种任务分别建立分析快照，不混用审阅决定。

入口固定为 `python <skill_dir>/scripts/material_agent.py`，其中 `<skill_dir>` 是本 Skill 实际所在目录。首次运行、换电脑或依赖报错时读取 [CLI 与迁移](references/cli.md)，运行 `doctor`。核心随 Skill 携带，不需要原项目目录或模型 API 密钥；AI 的语义审阅由当前 Codex 会话完成。

## 执行

1. **建立广泛合同底稿。** 调用 `analyze`，读取 `task.json` 和审阅表；覆盖正文、附件、跨条款引用及未在模板展示的字段，保留原文、位置、条件、单位、份额和版本。底稿仍是候选；原文保留、结构化提取和事实核验分别判断，未检出不等于合同没有。
2. **识别模板范围与原子需求。** 逐物料检查 `material_id → region_id → slot_id`。`target` 是选中的模板区域，`other` 是未选区域；多主体时由 AI 按封面、要素表及上下文选主体，必要时维护 `--template-map`，见 [CLI](references/cli.md)。信托模板只用自身要素页，合同与底层同名也不能转选底层。再读标签、正文、括号、脚注、空白值和图片文字，把一槽中的费率、计提、支付等分别列为需求，未知字段先在本任务定义，见 [需求发现与合同回查](references/requirements.md)。
3. **核对适用性并回查补提。** 先判断模板要求对合同产品是否适用，再匹配底稿。证据不足时用 `search-contract` 检索完整条款及相关附件，由 AI 核对上下文并登记合同补提；补提保持合同来源，不伪装成用户提供。模板旧值只说明展示需求，不能证明目标事实。查无可用依据、条款冲突、原文不可读及明确不适用分别记录；闭锁或封闭产品不因模板有开放日就虚构日期。
4. **补缺与生成表达。** 只有回查后仍需要的外部信息才列给用户，说明“位置｜原子需求｜已查依据｜仍需补充”。按每份模板的顺序、句式、标题/摘要方式生成文字；事实相同可复用，表达需求分别核对。缺项清理旧值为待补占位；确实不适用须有依据。由 AI 维护 [review.json](references/review.md)，记录每项需求的依据及最终文字，并为每槽填写处置。
5. **检查后生成交付文件。** 用 `inspect-review` 检查需求覆盖及审阅关联，再执行已授权、有依据的决定，无需重复逐文件批准。按物料实际用途识别 PPT、一页通或海报；PPTX 也可能是一页通或海报，必要时由 AI 填写 `review.delivery_plan`。`apply` 将完整审阅稿放入 `internal/`，自动把用户文件放入 `delivery/` 并登记交付清单。Word 基于清洁基线生成本次真实修订与锚定批注，保留原批注；PPT 保留对象并局部改文，只输出需修改的选定主体要素页。选页受阻时保留待处理状态，不能交付完整 PPT 作为替代。
6. **核验实际成品。** 运行 `validate`，逐项检查“模板需求—合同或有效补充依据—最终文字”，按 [验收与交付](references/qa-and-delivery.md) 打开并检查清单中的每份最终文件，再执行 `accept`。只验收 `internal/` 中的完整稿不算交付验收。核对标题、脚注、页眉页脚及图片中的遗漏，分别报告文件完整性、内容核对、原生与视觉检查结果。

## 完成口径

最终只链接 `delivery_manifest.json` 中实际生成的用户文件：一页通、海报沿用模板文件名，PPT 在模板原文件名的扩展名前加“产品要素”，不加 ID、“审阅稿”或“更新稿”后缀；同名文件用物料 ID 子目录区分。PPT 说明保留的原页码和输出页数，并列简短修改/待补清单。

所选内容既要完成逐槽处置，也要完成逐项原子需求的发现、依据与表达核对；候选需求不能自动标为已发现完整。待补占位、未审需求、准备/编辑受阻和未验收均不能宣布全部完成。Word 交付只保留本次修订；其中本次删除的基线文字属于审阅历史，同时核对本次修订全部接受后的正文，不自动接受这轮新修订。

样例配置和历史出现频次不是通用必填规则。新字段可在任务内使用，复核具有复用价值后再维护公共字典。通用语义由 AI 审阅，CLI 不保证自动理解任意合同。保留来源与版本；资料或引擎改变时重新分析，不能改哈希、身份状态或验收值绕过检查。
