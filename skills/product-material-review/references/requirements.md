# 需求发现、合同回查与逐项核对

本流程用于默认 `template` 模式，由 AI 维护审阅记录。字段字典是复用词汇，不是提取白名单；标签相同也不代表内容只需一个事实。自动需求候选是检查起点，不代表模板已经读全。

## 从模板发现需求

在已选定模板主体的交付范围内，逐槽阅读标签、值、括号、脚注、表头、空白格及句中参数；同时查看标题、页眉页脚和图片中的实际文字。图片未解析时保留未核状态，不能因没有文字槽位就视为没有需求。

每个槽位可以对应多条原子需求。分别记录事实、条件和展示要求，例如“管理费年费率……，每日计提、按季支付”至少包含费率、计提频率和支付频率；还应检查份额、年计息天数、阶段条件等是否构成本次实际需求。标题、摘要方式、句式等作为 `display_rule`，具体旧数值不当作合同证据。

AI 读取 `task.requirement_candidates`，将每个候选纳入已发现需求，必要时继续拆分并补充未被规则识别的要求。不能只逐条接受种子而省略原文检查。未知标签先解释其业务含义，映射已有字段或在当前任务定义新字段，不必先改公共字典。

## 先判断适用性，再找事实

对每项需求依次核对：

1. **是否适用。** 阅读目标合同中的产品类型、运行方式和约束；模板有某字段，不等于目标产品具有该业务。只有明确依据才能判为不适用。
2. **底稿是否足够。** 不仅匹配字段名称，还核对完整条款、份额、渠道、期间、单位及例外。
3. **回查合同。** 不足时使用 `search-contract`，尝试字段名称、近义词和所在业务环节；阅读命中条款、前后文、附件及引用关系。无命中不是“合同未规定”的证明，检索结果也不是已核实答案。
4. **登记补提。** 合同中找到的新事实放入 `contract_rechecks`，绑定本次合同哈希、原文块和准确引文；它仍是合同依据，不放进 `supplements`。
5. **确定仍未解决的原因。** 只有应适用、完成回查后仍需公告或渠道参数等外部事实时，列给用户补充。待定位、来源不可读、条款冲突和明确不适用分别记录。

## 任务内字段与合同补提

`review.new_fields` 每项包含：

| 字段 | 要求 |
| --- | --- |
| `field_id` | 本任务唯一，且不能与任务字典已有 ID 重复 |
| `name`、`definition` | 非空；说明具体含义、边界及与近似字段的区别 |
| `aliases` | 可选字符串数组 |

`review.contract_rechecks` 每项包含：

| 字段 | 要求 |
| --- | --- |
| `recheck_id`、`field_id` | 唯一补提 ID；字段须已在任务字典或 `new_fields` 中定义 |
| `value` | AI 核对原文后提取的值，保留条件和单位；不适用可表达为 `{"state":"not_applicable","value":null}` |
| `citations` | 数组，每项 `{ "block_id": "本合同原文块ID", "quote": "块内准确非空引文" }` |
| `source_sha256` | 本任务合同的来源哈希 |
| `reason`、`reviewed` | 说明原文如何支持所提内容，审阅完成时为 `true` |

CLI 检查原文件及转换版哈希、块 ID 和精确引文；AI 仍需判断条款含义、例外和适用性。有效补提保持 `source_kind=contract_recheck`，后续依据写为 `{ "type":"recheck", "id":"本次recheck_id" }`。

## 原子需求记录

`review.requirements` 的每项对应一个要核对的信息要求：

| 字段 | 用途 |
| --- | --- |
| `requirement_id`、`material_id`、`slot_id` | 唯一需求 ID 及所属模板槽位 |
| `field_id`、`description` | 对应字段及本次具体要求；未知字段先在 `new_fields` 定义 |
| `template_quote` | 本槽内实际支持该需求的模板文字；只说明需求，不证明目标值 |
| `display_rule` | 句式、完整条款/标题/摘要、单位及应保留的条件 |
| `candidate_id` | 来自自动候选时记录其实际 ID；继续拆分可多项关联同一候选，AI 额外发现的需求可省略 |
| `field_mapping_reason` | 需要解释候选字段映射或拆分时填写具体理由 |
| `status` | 下表中的状态 |
| `contract_search` | `needs_external` 的回查记录：非空 `queries` 字符串数组、本合同 `source_sha256`、说明已查规则及仍缺原因的非空 `conclusion` |
| `evidence` | 本次 `fact`、`recheck` 或 `supplement` 引用；未决状态可为空数组，不能据此判已核实 |
| `rendered_text` | 该需求在最终槽文中的实际表达；一般需求须有依据，指定模板保留例外与 `retained_text` 完全一致 |
| `removed_text` | 混合槽位中以空 `rendered_text` 移除不适用需求时填写：模板中唯一的精确片段，最终正文已不存在，并关联该需求的实际删除/替换决定 |
| `reason`、`reviewed` | 核对过程及结论，实质审阅完成后标记 `true` |

| `status` | 含义 |
| --- | --- |
| `verified` | 适用，事实和展示表达已核实 |
| `not_applicable` | 须有 `fact` 或 `recheck` 合同依据支持，不可仅凭外部补充；可保留“不适用”表达，或以空 `rendered_text` 表示有依据地移除该子需求 |
| `needs_external` | 已记录并回放合同检索，AI 阅读后判断仍缺本次应适用的外部信息；未记录回查时有效状态仍为 `unresolved` |
| `template_retained` | 仅指定业绩报酬或代销评级例外：合同未给出具体值，按用户规则原样保留模板并实际加注；单独计数，不属于 `verified` |
| `unresolved` | 尚未找到足够依据或含义仍待厘清 |
| `unreadable` | 所需原文无法可靠读取 |
| `conflict` | 存在未解决的条款或来源冲突 |

填写 `needs_external` 前，在该需求记录 `contract_search`，例如：

```json
{
  "queries": ["下一开放期", "开放日", "公告"],
  "source_sha256": "本任务合同的实际SHA256",
  "conclusion": "说明实际命中的一般开放规则、公告约定及位置，以及为何仍需本次日期的外部依据。"
}
```

CLI 回放这些查询，在 `requirement_coverage.contract_searches` 中记录真实命中数、原文块、截断情况及警告；自报命中数不作为结果。缺少回查记录的需求进入 `needs_contract_search_ids`，`effective_statuses` 仍为 `unresolved`，不能直接列为已查清、等待用户补充的缺项。来源变更或不可用会拒绝核对，不可读内容仍待查。`absence_proven` 始终为 `false`：有检索记录和零命中都不能证明语义上的不存在，结论仍须 AI 阅读原文及上下文判断。

同一槽位的全部需求 ID（含未决项）由 `slot_dispositions[].requirement_ids` 精确关联。每个槽位还要填写 `discovery_reviewed: true` 和 `discovery_reason`，说明已检查整槽及相关上下文、如何拆分；明确的静态标题可以没有事实需求，但仍需确认。

事实替换的 `decisions[].requirement_ids` 关联本槽已核实或有依据不适用的需求，其依据须来自这些需求。完成的表达通过 `rendered_text` 与实际最终槽文逐项绑定，不能只证明槽位“改过了”。不适用子需求需移除时，混合槽必须记录 `removed_text` 并落实到实际文字修改；整槽使用 `not_applicable` 且最终为空或“不适用”时无需另列删除片段。原本正确的“不适用”表达可有依据保留，不必制造修改。未决需求的 `rendered_text` 可暂为空，不能借此标为已完成；整槽被换为 `【待补充】` 时，已知子项可保留在底稿，整槽仍是待核。具体替换和槽位处置见 [审阅文件与依据](review.md)。

## 三个最小例子

业绩报酬及代销机构销售评级的额外保留记录、强制回查及批注关联见 [模板保留例外](template-retention.md)。其余字段继续采用上述一般缺项流程。

- **复合字段：** 模板“管理费……，每日计提、按季支付”。拆成三个需求，分别核对；合同只找到费率时，不能把整槽标为已核实，也不能沿用模板的计提/支付频率。
- **新增字段：** 模板新增“最低保有份额”，字典尚无此项。任务内定义其与首次认购门槛的区别，回查赎回、账户份额和强制赎回条款，以原文引用登记补提，再按模板展示。不能简单映射成“最低申购金额”。
- **明确不适用：** 模板写“下一开放期首个开放日……”，目标合同明确为无定期开放安排的封闭式产品。引用合同核对其适用性，把该日期需求标为不适用并相应改写/移除旧表达；不能强迫用户编一个开放日期。仅凭未搜索到日期不够判不适用。

所有例子均说明核对方式，不是针对任何具体产品的预设结论。每次以本合同和本模板证据判断。
