# 验收与交付

## 交付入口与命名

新分析任务的 `delivery_required=true`。含历史修订的 Word 物料先通过 [工作副本准备](cli.md#word-物料准备)：原件不变、原有全部修订已接受、原批注保留，原件和准备副本的双哈希可追溯；无历史修订时沿用原件作为清洁基线，合同不执行修订接受。准备受阻时不生成替代成品。正常流程中的 `apply` 同时生成两层结果，无需再把手动 `deliver-ppt` 作为必做步骤：

| 位置 | 用途 |
| --- | --- |
| `internal/` | 完整审阅稿，供来源对比、修改验证和追溯 |
| `delivery/` | 实际给用户的文件；PPTX 按安全选页规则导出 |
| `update_result.json` 的 `deliveries`、`delivery_manifest.json` | 逐物料记录交付文件、哈希、页码及状态；`delivery_manifest` 指向清单路径 |

按物料用途命名，不能仅凭扩展名决定：

| `kind` | 文件名示例 |
| --- | --- |
| `onepager`（一页通） | `【对客202610】旧产品一页通.docx` → `【对客202610】合同产品一页通.docx`；PPTX 同样更新产品 |
| `poster`（海报） | `【中行版】旧产品海报.pptx` → `【中行版】合同产品海报.pptx`；DOCX 同样更新产品 |
| `ppt` | `【PPT202610】旧产品.pptx` → `【PPT202610】合同产品产品要素.pptx` |

命名以 `task.contract.product` 为准，只替换已选模板主体，不取底层产品。优先匹配完整名称、已识别别名或去掉法律类型后缀的简称，兼容空格、中点及括号差异。无法可靠定位旧产品名时，用合同产品和可确认的渠道、日期、物料类型重新生成，避免遗留旧产品；查看交付记录的 `naming_metadata`。通用无产品名模板也补入合同产品名。Word 使用上传原件名而非准备副本名。

不加 ID、“审阅稿”或“更新稿”等文件名后缀。不同输入重名时放入各自 `material_id` 子目录，保留上述文件名。识别不清时由 AI 填写 [交付计划](review.md#交付计划)，不要让用户手写 JSON。

每条交付记录的 `status=ready` 表示文件已生成，含 `output` 和 `output_sha256`；`status=blocked` 只有阻塞原因，没有可交付文件。PPT 选页、混页或内容处理受阻时，不能改交 `internal/` 完整稿。`ready` 不代表已完成内容和视觉验收。文件可以同时为 `ready` 与 `content_status=pending_draft`：已把待确认原值保留、局部标黄并加批注时可交付，不要求先补齐参数；未决事实仍单列。

## 分别判断完整性、内容与视觉

| 检查层次 | 判读方式 |
| --- | --- |
| 文件与关联完整性 | `validate` 核对来源、审阅决定、哈希、局部修改及交付文件；`passed=true` 仍不证明语义或版面正确 |
| 内容核对 | `content_reviewed` 表示模板内容核对完成；`pending_draft` 表示含 `template_pending` 或其他未决信息，可交付已生成文件但不能宣布事实全部完成；旧 `content_reviewed_with_template_exceptions` 仅兼容历史模板例外；`blocked` 无可用交付；同品 `review` 模式 PPT 的 `reviewed_output` 仍须对照未决检查 |
| 原生与视觉 | 初始 `native_opened=false`、`visual_status=not_checked`；只有实际检查绑定的最终文件后才记录通过 |

内部结果的 `updated_with_pending_checks` 表示已改但仍待核，`updated_pending_visual_qa` 表示仍待版面验收。`edit_blocked_source_copy` 和 `pending_review_source_copy` 不生成最终交付文件。`unchanged_source_copy` 表示未执行文字修改，不能说已改文；如内容经合同核实可保留，仍须完成相应需求、槽位及最终文件验收。读取 `verification.issues` 和未决检查说明具体限制。

模板模式逐项核对原子需求与槽位：未知字段已定义、复合要求已拆分、合同补提绑定原文、`rendered_text` 与实际槽文一致。`final_text` 只核对局部编辑后的结果，不要求重新撰写。`template_pending` 的原值、标黄和批注须同时实际存在，独立计入待确认清单，不增加合同核实或完成数。已确认的静态标签可沿用自动记录。

对新模板任务逐项验收：

1. 已改事实与合同依据一致；同主体风险 R 值和风险描述一致。
2. 待确认原值与基线片段逐字一致，所有应提示的出现位置均有黄色标记，旁边原句不整段染黄。
3. 每项保留参数关联真实简短批注，重复值按跨度定位，不能错标另一个相同值。
4. 修改/标记跨度之外的文字、格式与对象保持；中文措辞或条件确需调整时有具体 `wording_change_reason`，无无依据的润色。
5. 独立核对输出的实际标黄范围、批注锚点和本轮 Word 修订；只核对审阅 JSON 或依靠同一写入逻辑重放不够。

`inspect-review` 检查回写前的审阅记录，`validate` 检查实际结果；二者不证明 AI 已完整理解合同。共同检查可能在多份物料重复出现，对用户列缺项时按 `check_id` 去重。

## PPTX 选页范围

所有 PPTX 交付都执行安全选页，包括用 PPTX 制作的一页通和海报。页码为源文件的 1-based 页码，升序、无重复；选页计划不能扩大可编辑主体范围。

1. 模板模式按已选源模板主体及要素表证据选择需要修改的主体要素页，保留全部续表；相邻页重复“产品要素”标题、无标题的同列结构字段表，也应检查承接关系。CLI 记录 `continuation` 证据和待核页，不能只找“续”字；`review` 模式才按合同产品身份选择。合同与模板不同名不构成错误，也不能因此转选模板中的其他产品。
2. 信托模板只输出信托自身要素页，排除底层资管和其他产品要素页。封面、业绩、市场观点、策略介绍、免责声明和机构介绍不因出现产品名就成为要素页。
3. 页内混有未选产品，或要素区域主体归属仍待核时，不能整页导出。手动页码和理由不能绕过检查，也不能漏选已确认或待核的要素续页；待核范围先解决，再交付。需要仅保留混页中的选定区域时须另做对象隔离并验证，当前 CLI 不执行对象级隔离。
4. 关系完整性或指向被删除页面的链接导致选页失败时，先处理具体问题；阻塞状态不能回退为完整 PPT。

当前选页识别依赖常见要素字段与版面证据。整张表只有任务新定义字段时，可能仍需补充选页识别规则；合同补提完成不等于选页一定成功。遇到此类保守阻断应检查真实页面并说明限制，不以手工页码强行绕过或改交完整稿。

PPTX 同时生成 `.delivery.json`，记录 `slide_mapping`、来源/输出哈希、结构校验、包含/排除的修改决定和初始视觉状态。检查实际输出页数、页序及对应源页码；完整稿中被排除页面上的修改不属于最终交付。

## 原生、视觉与验收记录

打开清单列出的实际文件，不以完整内部稿的截图或打开记录替代交付检查：

- Word：确认上传原件未改变；原件有历史修订时，准备副本已接受全部旧修订且原批注保留。最终文件只含本次真实修订，原批注和本次新增锚定批注可见。按本次修订全部接受后的正文视图核对已改事实及标黄待确认原值，表格、分页、字体和行距正常；检查黄色仅覆盖参数、原批注及新增锚点正确。本次删除的基线文字属于审阅历史，不应混入原有未接受的修订；另检查当前可见正文是否残留未经授权的旧事实，交付时保留这轮新修订。
- PPTX：页数、原页码映射和主体范围正确；对象可编辑，表格、换行、溢出和依赖正常；实际黄色参数和原生批注可见，未修改无关文字；没有带出底层或其他产品页。
- 内容：核对标题、脚注、页眉页脚、图片文字和空白槽位；名称按合同，其他费用、日期、渠道和条款有本次依据或原值保留待确认标记。分别检查复合需求，不能以整段合同引用替代逐项核对。

渲染页面可以帮助检查版面；原生打开和视觉审阅按实际执行分别记录。无相应能力或尚未检查时保持未验收，不把自动初始状态改写为通过。

`acceptance.json` 包含 `task_id`、覆盖内部结果的 `materials` 数组，以及最终交付文件的 `deliveries` 数组。两组记录共用以下字段，分别绑定各自实际文件：

| 字段 | 值 |
| --- | --- |
| `material_id` | 本任务实际物料 ID |
| `output_sha256` | 对应内部输出或交付文件的实际哈希 |
| `native_opened` | 实际完成原生打开时为 `true` |
| `visual_reviewed` | 实际检查版面并通过时为 `true` |
| `reviewer` | 实际审阅者/执行代理身份 |
| `notes` | 实际检查页码、方法、发现及限制 |

`materials` 必须覆盖全部内部结果。`deliveries` 可以暂缺或只记录已检查文件；缺失的最终文件保持未验收，不能全部完成。提供的交付 QA 必须对应 `ready` 文件、不重复且哈希一致。执行 `accept` 后，验收结果会更新 `deliveries` 的 `native_opened`、`visual_status` 和 `acceptance`；初始 `delivery_manifest.json` 保留生成时状态，不手工修改它来代替验收。

只有全部物料的交付均为 `ready`、内容与所需检查完成、内部结果及每个最终文件的原生与视觉检查通过，才能 `all_updates_complete=true`。只有内部稿 QA、只有安全选页、只有 `validate` 通过或仍有待补项均不能全部完成。不要填写未执行的检查。

## 最终答复

只链接交付清单中 `ready` 且实际存在的用户文件；验收后的状态以 `accepted_result.json` 为准。PPT 说明保留的源页码和输出页数。分开列修改清单与待确认清单，后者写位置、保留原值和缺少的具体参数，分别说明内容与视觉验收。`ready` 且标注清楚的 `pending_draft` 可以交付；阻塞项说明原因，不链接内部完整稿作为替代成品。
