# 验收与 PPT 产品要素页交付

## 先读每份结果

| 状态 | 实际含义 |
| --- | --- |
| `updated_with_pending_checks` | 已局部修改，仍有非 info 未决检查 |
| `updated_pending_visual_qa` | 已局部修改且无剩余非 info 检查，仍待版面验收 |
| `edit_blocked_source_copy` | 编辑受阻，输出是原文件副本；查看 `verification.issues` |
| `pending_review_source_copy` | 未执行修改，输出原文件副本且仍待核 |
| `unchanged_source_copy` | 未执行修改且无剩余检查；不能表述为已更新文字 |

`validate` 重新验证来源、审阅决定、输出哈希和实际局部修改。它返回 `passed=true` 仍可能伴随待核项和 `visual_status=not_checked`。`pending_review_count` 可能在多个物料中重复累计共同问题；对用户报告缺项时按 `check_id` 去重。

模板模式还需同时检查原子需求和每个选中槽位：需求是否由 AI 逐句检查、候选是否已覆盖、未知字段是否已定义、合同补提是否绑定准确原文、各需求的依据及 `rendered_text` 是否与真实最终文字一致。只替换产品名、只填写补充信息、遗漏复合字段子要求或保留模板旧值均不能视为完成。占位和未决内容可留在明确标注的内部待核稿中，不能进入“全部完成”结论或冒充最终 PPT 要素页。

`inspect-review` 适合在回写前发现审阅记录中的缺口；`validate` 还要对照实际输出。二者校验来源、结构、关联和状态，不能证明 AI 已理解所有条款；语义核对和原生/视觉检查仍由执行代理完成。

## 原生与视觉检查

在 Word/PowerPoint 打开实际输出文件，并按实际变更范围核对：

- Word：真实修订与批注可见，接受修订后的正文符合合同，分页、表格、字体及行距正常。删除修订保留的旧模板名称属于审阅历史，不应因其仍在 XML 中就误判为正文残留。
- PPT：改字对象正确，换行、溢出和表格正常；选中模板区域已转换为合同产品，未选产品对象保持原样。最终选页副本不包含这些未选产品页。
- 内容覆盖：逐页核对标题、表格正文、未映射文字、空白槽位、图片内文字及页眉页脚；所有具体名称、日期、费用、渠道和条款都须有本次依据或清楚的待补状态。静态格式保留不代表旧业务内容可保留。
- 复合要求：例如管理费的费率、计提与支付分别核对；某子要求不适用时检查其依据及实际删除/改写。不能因整段引用过合同就跳过逐项检查。
- 来源与输出：输出指向本次版本；源文件未改变；受阻文件没有误报为成功。

可用渲染工具导出页面图片检查版式；原生打开和渲染各自记录实际完成的事实。原稿已有问题与本次新增问题分开说明。没有相应能力或尚未实际检查时保持未验收状态。

`acceptance.json` 由 AI 根据真实检查结果生成，包含 `task_id` 及覆盖全部物料的 `materials` 数组。每项为：

| 字段 | 值 |
| --- | --- |
| `material_id` | 当前任务的实际物料 ID |
| `output_sha256` | `update_result.json` 中对应输出哈希，并核对实际文件 |
| `native_opened` | 实际完成原生打开时为 `true`，否则 `false` |
| `visual_reviewed` | 实际检查版面且通过时为 `true`，否则 `false` |
| `reviewer` | 实际审阅者/执行代理身份 |
| `notes` | 检查页码/幻灯片、方式、发现和限制 |

调用 `accept` 后，只有全部非 info 检查结案、所需原子需求和槽位处置完成且实际文字一致、全部原生打开和视觉检查通过，才可能 `all_updates_complete=true`。待补占位、待定位、冲突、不可读、源副本或局部改名不能满足完整制作验收。不要为了“完成”把未核信息结案或将未执行检查写成 `true`。

## 只交付产品要素页

PPT 的最终交付物是完成内容核对的选中产品要素页副本；完整更新稿留在本次工作目录，用于审阅、来源对比和校验。模板模式先按模板自身主体选择要素页，再按合同转换内容；同品 `review` 模式按合同产品选择。完成槽位和原子需求核对并通过回写检查后，用 `deliver-ppt --task ... --result ... --material-id ... --out ...` 生成选页副本；未完成的模板核对不能靠选页变为最终稿。参数示例见 [CLI](cli.md)。默认采用无歧义的选中要素页建议。需显式选页时提供 `--pages` 和 `--review-reason`，逐页记录实际依据；手动参数不能放行未选产品专属页、混页或身份待核要素页。

选页按原始 PPT 的 1-based 页码核对，保持原顺序且不重复：

1. 模板模式以本次选定的源模板主体及页内要素表/字段证据选择页面，必要的续表一并保留；不要拿合同名称反向挑选模板中的其他产品页。`review` 模式才用合同产品身份选择。
2. 封面、市场观点、策略介绍、历史业绩、免责声明或机构介绍不因出现产品名称自动变成要素页。
3. 使用信托模板时，只更新并输出信托自身要素页，排除底层资管及其他产品要素页。合同恰与底层资管同名时仍遵守模板主体选择，不能误选底层页。源模板主体和合同目标不同名是正常跨产品制作，不构成拒绝理由。
4. 同页混有其他产品时，禁止整页输出；`--pages` 与 `--review-reason` 不能作为例外。若必须使用该页的目标内容，另行制作仅含目标产品区域、保留可编辑对象的副本，并核对来源、完整性和版式；当前 CLI 不提供对象级隔离，不能声称选页已完成隔离。原完整稿中的其他产品对象保持原样。
5. 页内存在主体归属不明的要素区域时，先核对模板上下文、补充选择依据并重新分析；不能靠手动页码绕过区域检查。可先交付其他无歧义要素页，并明确剩余页面的处理状态。

选页模块保留所选页的原生对象及依赖，并检验关系完整性；指向被删除页面的内部链接可能阻塞导出。遇到拒绝时说明具体原因，先解决链接/页范围问题，不能把完整 PPT 改名冒充“产品要素页”。

导出同时产生同名 `.delivery.json`，例如 `产品要素页.pptx` 对应 `产品要素页.delivery.json`。该记录包括 `slide_mapping`、来源/输出哈希、结构校验、`included_decisions`、`excluded_decisions` 和初始 `visual_status="not_checked"`。完整稿中落在排除页面的修改不属于最终 PPT 交付。

导出后核对实际页数、页序、每页对应原页码、文字和对象；原生打开选页副本并检查版面。选择出正确页数不代表缺项已解决；选页副本继承对应内容的未决状态。完整更新稿的 `accept` 记录只覆盖其绑定哈希，不能直接充当新选页副本的验收记录。当前 CLI 没有选页副本专用 `accept` 子命令；另保存可读验收记录，注明副本路径、实际输出哈希、检查方式和页码，交付时说明实际检查结果，不把自动 sidecar 的初始状态冒充已验收。

## 对用户的最终说明

链接 Word 审阅稿和 PPT 产品要素页副本，简要说明改了什么、PPT 保留哪些原始页码、还有哪些信息待补、哪些检查未完成。明确的待核稿可以先交付；结论应与实际状态一致。
